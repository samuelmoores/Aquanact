Window System
-------------
Source Files: `src/Engine/Window.cpp`, `include/Engine/Window.h`
Book Reference: Chapter 6.1, Subsystem Start-Up and Shut-Down; Chapter 9, Human Interface Devices
Engine Notes:
	-Window.h creates GLFW window and OpenGL context
	-owns buffer swapping and event polling
	-frame buffer size queries
	-window close state
	-startUp() init GLFW, creates window, create openGL context, makes it current, sets vsync and default window state
	-SwapBuffers() presents rendered frame, PollEvents() pumps OS event queue, GetFramebuferSize() gives render code drawable size
	-RenderManager, Input and FrontEndManager depend on it and is bottom-most app owned runtime service

Gregory Alignment:
	-classic low level engine service, small, essential and dependency root for higher level services

Deviations / Risks:
	-coupled with graphics device so not a true window class for vulkan or DX graphics
	-should only create and manage OS window, own input callbacks or have nearby platform layer with no rendering setup
	-presentation responsibility, framebuffer size and render target size, renderer assumption about context

Render Manager
--------------
Source Files: `src/Engine/RenderManager.cpp`, `include/Engine/RenderManager.h`
Book Reference: Chapter 8.1, The Rendering Loop; Chapter 11, Rendering; Chapter 12.8, Overlays and User Interfaces
Engine Notes:
	-Loop(), per frame render path, build render commands, flushes through active camera, draws UI, presents frame
	-Submit(RenderCommand&), Queues renderable object for the current frame
	-Flush(Camera&), sends queued command to the graphics device
	-main bridge between game/world state and graphics backend

Gregory Alignment:
	-separated from gameplay and platform
	-prevents game code from calling graphics functions
	-centralizes camera and lighting

Deviations / Risks:
	-carries specific OpenGL functionality
	-mixes with diagnostics, editor overlay and runtime UI coordination
	-get rid of backend graphics specifics, UI/debug repsonsibilities

Book Reference: Chapter 1.6, Tools and the Asset Pipeline; Chapter 7, Resources and the File System
Engine Notes:
	-bridge between disk and runtime

Gregory Alignment:
	-centralized project state
	-loading and saving separate from gameplay
	-clear project path
	-boot time restoration separate from frame loop

Deviations / Risks:
	-coupled to other systems through globals
	-handles too much session reconstruction
	-should not be storing live engine state, just project I/O
	-can become a catch all for policy in regard to loading, serialization and runtime reconstruction
	-boundary blurring between gameplay and UI
	-should look to move stuff into ProjectStateSerializer, LevelManager, GameGUIManager and asset/content loaders
