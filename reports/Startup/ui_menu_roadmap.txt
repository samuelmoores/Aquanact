Report: Menu and UI Screen Architecture

Current direction:
- `Level` should remain the gameplay/world container.
- Menus should become their own UI-only concept, not fake levels.
- `GameGUIAsset` should stay the visual/layout layer underneath both menus and in-game UI.
- The long-term UI system should support multiple screen types:
  - `Menu`
  - `HUD`
  - `Overlay`

Why this matters:
- It removes level-only systems from menu screens.
- It avoids special-casing 3D engine concerns for UI-only content.
- It makes HUD, inventory, crafting, pause, and dialogue easier to add later.
- It keeps the engine/editor model aligned with how the game actually behaves.

Recommended design:
- `Level` = gameplay world, entities, lighting, camera, physics, etc.
- `Menu` = UI-only screen that owns one `GameGUIAsset`
- `UIScreen` or `UIState` = runtime wrapper for menus, HUD, overlays
- `GameGUIAsset` = widget layout and bindings only

Best evolution path:
1. Add a `Menu` type separate from `Level`.
2. Keep `GameGUIAsset` as the asset menu screens reference.
3. Add a screen/state layer that can manage:
   - startup menu
   - HUD
   - inventory overlay
   - pause menu
4. Use a stack or layered model so HUD can stay visible while overlays open.

Implementation implications:
- Startup can target either a `Level` or a `Menu`.
- A menu can be the first thing shown at launch.
- In-game UI can be layered on top of gameplay without changing the world model.
- Inventory/crafting can be implemented as overlay screens bound to gameplay components.

Risks / design decisions to settle:
- Whether menus are project assets or runtime definitions.
- Whether HUD is one global screen or one per level.
- Whether overlays pause gameplay or just block input.
- How much of the current `GameGUIManager` should be reused versus split into `UIManager`.
