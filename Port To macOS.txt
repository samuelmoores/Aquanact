Aquanact: Port To macOS
======================

Goal
----
Build and run the Aquanact editor and standalone game natively on macOS while
preserving the existing Windows build. Keep graphics backend choices modular:
the initial macOS implementation may use OpenGL, while a future Metal backend
must be addable without spreading backend-specific code through shared engine
systems.

Scope and constraints
--------------------
- First milestone: configure, compile, launch, and exercise the editor and game
  on a specified macOS version and Mac architecture (Apple Silicon or Intel).
- Keep Windows presets, compiler options, platform implementations, and runtime
  behavior working.
- Keep renderer-facing code independent of OpenGL and Metal implementation
  details. Use the existing GraphicsDevice / OpenGLGraphicsDevice boundary as
  the starting point and extend it deliberately where necessary.
- Treat web packaging as a separate follow-up. The current web build flow calls
  PowerShell and is not part of the first native macOS milestone.
- Do not claim a platform is supported until it has been built and exercised on
  that platform. Record the tested macOS version, architecture, and GPU.

Step 1: Record the target and establish a baseline
-------------------------------------------------

Acceptance: there is a defined Mac target and a known Windows baseline.

Step 4: Isolate operating-system-specific code
----------------------------------------------
1. Provide a normal `main` entry point for the macOS game executable. Keep the
   Windows `WinMain` implementation and its Windows header behind Windows-only
   guards.
2. Add a macOS implementation for locating the running executable's directory
   in FileSystem, keeping the existing Windows implementation unchanged.
3. Search all source and build scripts for Windows-only headers, APIs, link
   libraries, command invocations, path assumptions, and executable naming.
4. Keep each OS-specific implementation behind a small, explicit boundary so
   shared engine logic does not accumulate platform checks.

Acceptance: macOS targets no longer require Windows headers or libraries, and
Windows targets retain their existing entry point and file behavior.

Step 5: Make graphics backend selection explicit and modular
------------------------------------------------------------
1. Treat GraphicsDevice as the engine-facing graphics interface. Move any
   renderer-facing OpenGL-specific operations behind that interface instead of
   adding new direct OpenGL calls to shared engine or UI logic.
2. Keep OpenGL implementation code in OpenGLGraphicsDevice and closely related
   backend-specific files. Avoid leaking OpenGL types into general engine
   interfaces where a backend-neutral type is practical.
3. Add an explicit backend selection/factory seam so startup can select an
   implementation without making game/editor systems construct OpenGL classes
   directly.
4. Keep platform context/window setup separate from graphics-device behavior.
   GLFW may remain the initial window/context layer, but its macOS-specific
   context hints should not be mixed into renderer algorithms.
5. Document which operations the interface must expose for the editor, game,
   debug drawing, and UI integration. Add interface methods only for actual
   engine needs.
6. Keep GUI rendering integration behind a similarly clear boundary. MyGUI and
   ImGui currently use OpenGL integration, so a future Metal backend will need
   corresponding GUI renderers or a backend-neutral UI rendering layer.
7. Do not implement Metal as part of the first macOS build unless separately
   scoped. The initial goal is a clean OpenGL implementation behind the seam.

Acceptance: backend-independent systems depend on the graphics interface, and
OpenGL-specific code remains localized. A future Metal implementation has a
clear place to plug in without rewriting engine systems.

Step 6: Adapt OpenGL context creation for macOS
----------------------------------------------
1. The current Window setup requests OpenGL 3.3 compatibility. macOS requires a
   forward-compatible core profile for OpenGL 3.2 and later; the macOS path must
   request a supported core profile.
2. The project contains a GLSL 4.10 shader. Verify that the requested context
   and the actual target Mac GPU support OpenGL 4.1, or revise shader/context
   requirements consistently if support for a lower version is needed.
3. Keep Windows context behavior unchanged unless a shared fix is demonstrably
   safe and covered by Windows regression checks.
4. Check GLAD initialization and the order of context creation, function loading,
   and renderer startup.
5. Check framebuffer dimensions and viewport updates on Retina displays. Use
   framebuffer pixel dimensions rather than logical window dimensions for GL
   viewport setup.

Acceptance: the application creates the intended context on the target Mac,
reports its actual OpenGL version, initializes GLAD, and sets the correct
framebuffer viewport.

Primary risks and decision points
---------------------------------
- OpenGL context: the current compatibility-profile request is not suitable for
  macOS OpenGL 3.2+ contexts, which require core profile.
- OpenGL ceiling: macOS provides up to OpenGL 4.1; the project has a GLSL 4.10
  shader, so the actual GPU/context must support that requirement.
- Renderer compatibility: a successful compile does not prove compatibility
  with core profile. Editor-only drawing, GUI backends, and shader paths need
  runtime validation.
- Third-party GUI backends: MyGUI and ImGui currently use OpenGL integration.
  Metal support will require separate GUI backend work.
- Runtime assets and paths: running from a build directory can expose path
  assumptions that do not appear during compilation.
- Windows regression: all shared changes must preserve the current Windows
  build and runtime path.

Out of scope for the first milestone
------------------------------------
- Replacing OpenGL with Metal.
- Rewriting the renderer for a new graphics API.
- Porting the PowerShell web packaging flow unless web packaging is explicitly
  included in the Mac deliverable.
- Claiming support for untested macOS versions or GPU architectures.
